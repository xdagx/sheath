# XDAG wallet & transaction formats implemented by this extension

All byte layouts below were derived from the official sources and are verified by
cross-implementation test vectors (`tests/fixtures/*`, generated by `tools/vectors/*`).

## 1. Keys and addresses

| Item | Definition | Reference |
| --- | --- | --- |
| Curve | secp256k1, compressed public keys (33 bytes) | xdagj-crypto `ECKeyPair` |
| Mnemonic | BIP39 English, PBKDF2-HMAC-SHA512 × 2048, salt `"mnemonic"+passphrase` (empty) | `Bip39Mnemonic.mnemonicToSeed` |
| HD path | BIP32, `m/44'/586'/0'/0/i` (coin type 586) | `Bip44Wallet.deriveXdagKey`, XDAG Pro `Helper.getWalletByMnemonic` |
| Account id | `RIPEMD160(SHA256(compressedPubKey))`, 20 bytes | `AddressUtils.toBytesAddress` |
| Account address | `Base58(id ‖ SHA256d(id)[0..4])` — Base58Check **without** version byte | `Base58.encodeCheck` |
| Block address (2018) | standard Base64 of the 24 significant bytes of a block hash, 32 chars | xdag `address.c`, xdagj `BasicUtils.hash2Address` |

Base58 is a subset of the Base64 alphabet and account addresses can also be 32 characters
long, so an input is treated as a block address only if it is **not** valid Base58Check
(same precedence as xdagj's RPC `xdag_getBalance`).

## 2. xdagj `wallet.data` (version 4)

```
int32  version = 4                                   (big-endian)
bytes  salt (16)                                     (VLQ length prefix, big-endian base-128)
int32  n
n × { bytes iv (16), bytes AES(privateKey32) }       (VLQ length prefixes)
bytes  iv (16), bytes AES( string mnemonic ‖ int32 nextAccountIndex )
```

`key = BouncyCastle BCrypt.generate(utf8(password), salt, 12)` → 24 bytes → **AES-192**/CBC/PKCS#7.
BouncyCastle's raw BCrypt differs from the OpenBSD string format: no NUL terminator is appended,
an empty password is replaced by 4 zero bytes, and all 24 output bytes are used.
WebCrypto does not offer AES-192 in Chrome, so `@noble/ciphers` is used.
xdagj only accepts 12-word phrases in this file; the exporter writes an empty phrase otherwise.

## 3. 2018 C client: `wallet.dat` + `dnet_key.dat`

* `wallet.dat` / `wallet-testnet.dat`: `N × 32` bytes. Key *n* is the big-endian private key
  (`BN_bn2bin`) encrypted with `dfslib_encrypt_array(crypt, key, 8 words, n)`. The C client's
  default key is the **last** one.
* `dnet_key.dat`: 2048 bytes = dfsrsa private key ‖ public key (256 × uint32 each). Sector *i*
  (512 bytes) is encrypted with `dfslib_encrypt_sector(crypt, sector, ~i)`.
* `crypt` = `set_user_crypt(password)`: `dfslib_crypt_set_password` (UTF-8 → code points,
  4 × 32-bit accumulator with multiplier 1971772241), then 128 rounds of
  `dfslib_crypt_set_sector0` + `dfslib_encrypt_sector` over a fixed sector.
  An empty password — or one containing characters outside the BMP (4-byte UTF-8), which dfslib
  rejects — leaves the files unencrypted.
* Password check: in a correctly decrypted `dnet_key.dat` the private and public dfsrsa keys share
  the modulus (upper half of each key, after detecting repeated short ARM keys).

## 4. Transaction block (512 bytes = 16 × 32-byte fields)

Field 0 (header): `transport u64 = 0 | types u64 | time u64 | fee u64` (little-endian).
`types` holds 16 four-bit field types (field *i* at bits `4i..4i+3`).
Header type: `1` on mainnet, `8` on testnet/devnet.

| Type | Field | Layout |
| --- | --- | --- |
| 0xE | transaction nonce | 24 zero bytes ‖ nonce u64 LE |
| 0xC / 0xD | account input / output | 4 zero bytes ‖ reversed 20-byte id ‖ amount u64 LE |
| 0x2 | block input (2018 address) | 24 address bytes ‖ amount u64 LE |
| 0x9 | remark | ≤ 32 bytes printable ASCII, zero padded |
| 0x6 / 0x7 | public key (even / odd y) | 32-byte x coordinate |
| 0x5, 0x5 | output signature | r (32 BE), s (32 BE) |

Account transfer: `header, nonce, INPUT, OUTPUT, [REMARK], PUBKEY, SIG, SIG`, zero padding.
Legacy transfer: `header, IN, OUTPUT, [REMARK], PUBKEY, SIG, SIG` (no nonce, fee field 0).

* Amounts in link fields use the historic fixed point `xdag2amount(double)`:
  `floor(v) << 32 | ceil(frac(v) · 2³²)`, computed through a double exactly like Java.
* Header fee is in nano-XDAG and is the *extra* fee; the node charges `0.1 + extra` per output,
  deducted from the transferred amount (the recipient receives `amount − fee`).
* Time: `ceil(ms · 1024 / 1000 + 0.5)` (xdagj `XdagTime.msToXdagtimestamp`).
* Signature: RFC 6979 ECDSA, low-S, over `SHA256d(block with signature fields zeroed ‖ compressedPubKey)`.
* Block address returned by `xdag_sendRawTransaction`: `Base64(SHA256d(block)[0..24])`.

## 5. RPC methods used

`xdag_getBalance`, `xdag_getTransactionNonce`, `xdag_getAverageFee`, `xdag_sendRawTransaction`,
`xdag_getBlockByHash(address, page, pageSize)`, `xdag_netType`, `xdag_blockNumber`
(xdagj `io.xdag.rpc.api.XdagApi`).
